# 数据流

本文按“每一种操作”描述数据从哪里来、经过哪些函数、写到哪里、如何失败回退。函数名以当前源码为准。

通用约定：

- 评价由 MainAgent 编排；文档整理由 documents service 作为入口、调用拆分 Agent；子 Agent 只返回结果，不直接写 store；
- `AgentRun` 记录每个子 Agent 的阶段、状态、LLM 调用数和耗时；
- `requirementPoints`：需求点（表格规则点 + 文本候选点）；
- `designPoints`：设计点（设计表规则点 + 数据库/文本候选点）；
- `requirements` / `designUnits`：最终展示和评价使用的单元；
- `Campaign`：一次评价任务；
- `Relation`：一条需求→设计或设计→代码关系；
- `StoredDocument`：持久化的文档对象；
- 所有写操作经过 `store.mutateStore()`。

---

## 1. 项目创建与删除

### 创建

**触发入口**：`POST /api/projects`

**调用链**：

```text
projectsRouter.post
→ mutateStore
→ 写入 StoreData.projects
→ 创建项目上传目录
```

**输入**：`name`、`description`。

**持久化**：`data/app.db` 的 `projects` 表，`data/uploads/<projectId>/`。

**失败**：名称为空/项目不存在 → 400/404；目录创建失败 → 500。

### 删除

**触发入口**：`DELETE /api/projects/:projectId`

**调用链**：

```text
projectsRouter.delete
→ mutateStore
→ 删除 projects / documents / snapshots / campaigns
→ 删除 data/uploads/<projectId>
```

**边界**：级联删除不可恢复；评价报告随 Campaign 删除。

## 2. 需求文档上传与规则拆分

**触发入口**：`POST /api/projects/:projectId/documents`，`kind=srs`，`useLlm=true|false`。

**输入**：DOCX 文件、kind、useLlm。

**调用链**：

```text
documentsRouter.post
→ saveParsedDocument
→ parseBuffer(buffer, "srs")
→ parseDocxFile
→ parseRequirements
   → extractRequirementPoints
      ├─ 需求表 → 规则需求点（origin=rule, confidence=1.0）
      └─ 纯文字叶子章节 → 文本候选点（origin=llm, judged=false）
   → buildFallbackUnits（仅规则点生成回退单元）
→ mutateStore 写入 StoredDocument
```

**中间产物**：

- `requirements`：无 LLM 时仅规则需求单元；
- `requirementPoints`：全部规则点 + 文本候选点；
- `outline`、`stats`、`warnings`；
- `status=parsed`，`useLlm` 记录用户选择。

**持久化**：

```text
StoredDocument.requirements
StoredDocument.requirementPoints
StoredDocument.stats
StoredDocument.warnings
data/uploads/<projectId>/srs-*.docx
```

**后续**：

- 如果 `useLlm && settings.apiKey`：文档状态改为 `enriching`，异步 `runEnrichment`；
- 否则停留在 `parsed`，文本候选等待「LLM 整理」。

**失败**：

- 非 DOCX/空文件 → 400；
- DOCX 解析异常 → 上传失败，不写入文档；
- LLM 未配置 → 保留规则结果，warning 提示。

## 3. 需求 LLM 整理

**触发入口**：

- 上传时 `useLlm=true` 且 LLM 可用；
- `POST /api/projects/:projectId/documents/:docId/enrich`。

**调用链**：

```text
runEnrichment
→ runEnrichmentInternal
→ client.testConnection（失败则回退）
→ createAgentContext
→ runSubAgent(RequirementSplitAgent)
→ runRequirementAgent
   1. judgeTextRequirementPoints
      - 只处理 kind=text 的候选
      - 回填 judged/accepted/confidence/reason
   2. generateSubsystemTaxonomy
      - 统计 accepted 需求点的 chapterPath
      - LLM 生成 3–8 类子系统 + 路径映射
      - 兼容对象/裸类别数组；缺 assignments 时按 40 个章节分批补映射
   3. generateRequirementUnits
      - accepted 点生成标题/类型/摘要/义务/关键词
      - 使用 taxonomy 映射 subsystem
→ mutateStore
```

**合并规则**：

- 保留人工单元 `origin=manual`；
- 按 `pointId` 保留已有人工审核状态；
- 替换自动生成的单元；
- 删除的自动单元已移除对应点，重跑不会恢复。

**持久化**：

```text
requirements
requirementPoints（judged/accepted/confidence）
subsystemTaxonomy
stats
warnings
status=parsed
```

**失败回退**：

- 预检失败 → 整个文档保持规则回退，记录 warning；
- 阶段 A 批次失败 → 该批文本点未判定，规则点继续；
- 阶段 B 批次失败 → 对应点使用规则回退单元；
- 服务重启 → 残留 `enriching` 恢复为 `parsed` 并提示。

## 4. 需求文档重新拆分

**触发入口**：`POST /api/projects/:projectId/documents/:docId/reparse`

**调用链**：

```text
reparseDocument
→ 读取已上传 DOCX
→ parseBuffer
→ parseRequirements
→ mutateStore
```

**合并规则**：

- 重新生成 `requirements`、`requirementPoints`、`stats`、`warnings`；
- 保留 `origin=manual` 的需求单元；
- 清空旧 `subsystemTaxonomy`；
- 不保留旧自动单元。

**边界**：重新拆分只做确定性规则解析，不自动触发 LLM 整理；需要 LLM 单元时再点击「LLM 整理」。旧自动单元的 code/review 不保证保留，人工单元保留。

## 5. 需求单元手工新增/删除/审核

### 新增

`POST /api/projects/:projectId/requirements`

```text
addManualRequirement
→ latestSrs
→ buildManualRequirement
   - code = SRS-MAN-NNN
   - origin=manual
   - structureOrigin=manual
   - reviewStatus=confirmed
   - 自动摘要/义务/关键词
→ push requirements
→ recomputeRequirementStats
```

**持久化**：`StoredDocument.requirements`、`stats`。

**注意**：手工单元不创建 `RequirementPoint`；LLM 整理时通过 `origin=manual` 保留。

### 删除

`DELETE /api/projects/:projectId/requirements/:code`

```text
deleteRequirementUnit
→ 找到单元
→ 从 requirements 移除
→ 如果 pointId 存在，从 requirementPoints 移除
→ recomputeRequirementStats
```

**限制**：文档 `status=enriching` 时返回 409。

### 审核

`PATCH /api/projects/:projectId/requirements/:code`

- 修改 `type`、`reviewNote`、`reviewStatus`；
- `recomputeRequirementStats`；
- 不修改原始 DOCX。

## 6. 设计文档上传与规则拆分

**触发入口**：`POST /api/projects/:projectId/documents`，`kind=sdd`。

**调用链**：

```text
saveParsedDocument
→ parseBuffer(buffer, "sdd")
→ parseDesign
   → extractDesignPoints
      ├─ 结构化设计表 → 规则设计点（confidence=1.0）
      ├─ 数据库表 → 候选点（字段结构保留）
      └─ 文本叶子章节 → 候选点
   → buildFallbackDesignUnits（仅规则点）
→ mutateStore
```

**持久化**：`designUnits`、`designPoints`、`stats`、`warnings`、状态。

**后续**：与需求相同，按 `useLlm && apiKey` 启动 `runEnrichment`。

## 7. 设计 LLM 整理

**调用链**：

```text
runSubAgent(DesignSplitAgent)
→ runDesignAgent
→ judgeDesignPoints
   - 只处理 text/database 候选
   - 回填 judged/accepted/confidence/typeHint
→ generateSubsystemTaxonomy
→ generateDesignUnits
   - 结构化表保留 type/name/interface/input/output
   - 数据库表保留 fields
   - 子系统取 taxonomy 映射
→ mutateStore
```

**持久化**：`designUnits`、`designPoints`、`designSubsystemTaxonomy`、`stats`、`warnings`。

**回退**：

- 预检失败 → 规则回退；
- 阶段失败 → 对应点规则回退；
- 无 LLM → 仅结构化设计表单元。

## 8. 设计文档重新拆分

与需求重新拆分一致：

- 只做规则解析，不自动触发 LLM；
- 重新生成 `designUnits/designPoints/stats/warnings`；
- 保留 `origin=manual` 设计单元；
- 清空旧 `designSubsystemTaxonomy`；
- 不保留旧自动设计单元。

## 10. 代码快照登记

**触发入口**：`POST /api/projects/:projectId/snapshots`

**调用链**：

```text
snapshotsRouter.post
→ scanCodeSnapshot(projectId, rootPath, commit)
   → 遍历目录、过滤 node_modules/dist 等
   → extractSymbols
      - 文件/类/接口/函数/方法/路由/模型
   → buildCodeTree
→ mutateStore
```

**持久化**：

```text
CodeSnapshot.files
CodeSnapshot.symbols
CodeSnapshot.routes/models 统计
CodeSnapshot.stats
CodeSnapshot.commit
```

**失败**：目录不存在/不可读 → 400/500；跳过超大文件/目录。

## 11. 需求 → 设计评价

**触发入口**：

`POST /api/projects/:projectId/campaigns`

```json
{
  "levels": ["requirement_design"],
  "subsystems": [],
  "name": "评审任务"
}
```

**调用链**：

```text
campaignsRouter.post
→ 校验项目/最新 SRS/SDD
→ 创建 Campaign(status=queued)
→ void startCampaignRun
→ 立即 201

startCampaignRun
→ 读取最新文档
→ 读取 LLM 设置
→ client.testConnection
→ Campaign(status=running, phase=preparing)
→ runAgentEvaluation
→ runSubAgent(RequirementDesignJudgeAgent)
→ RequirementDesignJudgeAgent 调用 runEvaluation(requirement_design)
```

### 11.1 检索

```text
runEvaluation
→ 过滤子系统
→ buildHybridRetriever
   ├─ BM25F 字段索引
   ├─ Legacy 词面索引
   ├─ Dense 索引（如果配置 EMBEDDING_MODEL）
   └─ 可选 Cross-Encoder 配置
→ 对每条需求的每条义务 rank
→ RRF 融合 + 结构重排
→ Top 8
```

### 11.2 LLM 判定

```text
每条需求：
  取 Top 6 候选
  requirementPayload：标题/描述/说明/类型/子系统/义务 O1..On
  designPayload：code/type/name/summary/description/obligations/interface/input/output/fields
→ 4 条需求一批
→ client.chatJson
→ 返回 targetCoverages:
   designCode
   coveredObligations[]
   partialObligations[]
   conflictingObligations[]
   evidence
   confidence
```

### 11.3 聚合

```text
buildCoverageRelation
→ 校验 designCode 必须来自候选
→ 归一化义务 ID
→ 按设计合并
→ 每条义务：冲突 > 完整覆盖 > 部分覆盖 > 缺失
→ coverageRatio = (完整覆盖 + 0.5 × 部分覆盖) / 义务数
→ status:
   conflict → mismatch
   covered == all → satisfied
   covered/partial > 0 → partial
   else → missing
→ 置信度按义务最大证据置信度平均
```

### 11.4 汇总与持久化

```text
computeSummary(relations, designUnits, requirementCount)
→ score / requirementCoverage / counts / bySubsystem / byType / findings / gate
→ Campaign(status=completed, relations, summary, warnings, method)
```

**回退**：

- LLM 预检失败 → 整任务启发式；
- 单批失败 → 该批启发式，warning；
- 检索失败 → 回退 `rankDesignCandidates`；
- 无候选 → LLM 可能判 missing；
- 用户取消 → `cancelled`；
- 重启 → `failed`，提示重跑。

## 12. 设计 → 代码评价

**触发**：`levels` 含 `design_code`；需要 SDD + code snapshot，不需要 SRS。

```text
runAgentEvaluation
→ runSubAgent(DesignCodeJudgeAgent)
→ runEvaluation(design_code)
→ rankCodeCandidates(design, symbolIndex, 7)
   - 每文件最多 2 个，避免单文件占满
→ 3 个设计一批
→ client.chatJson
→ 校验 targetHandles 必须在候选
→ 生成 Relation(implemented/partial/missing/divergent)
→ computeSummary
```

**回退**：与需求→设计相同，单批失败走 `heuristicDesignRelation`。

## 16. LLM 设置读取/保存/连接测试

**读取**：`GET /api/settings`

- `publicSettings()` 读取有效配置；
- API Key 只返回 `hasApiKey/apiKeyHint`，不返回明文；
- 返回 `meta.configSource` 标识 `.env` 或设置页。

**保存**：`PUT /api/settings`

- 开发环境 `.env` 接管时返回 409；
- 校验 baseUrl/model；
- 保留或清空 API Key；
- 写入 `data/app.db` 的 `settings` 表。

**连接测试**：`POST /api/settings/test`

- 使用当前配置调用 `LlmClient.testConnection()`；
- 返回延迟/错误，不改文档或评价数据。

失败路径：URL 非法、模型为空、网络失败；不会影响已有文档。

## 17. 状态与并发约定

| 对象     | 状态                                                                  |
| -------- | --------------------------------------------------------------------- |
| Document | `parsed` / `parsing` / `enriching` / `failed`                 |
| Campaign | `queued` / `running` / `completed` / `failed` / `cancelled` |
| Relation | `pending` / `accepted` / `rejected`                             |

保护：

- 同一项目同时只允许一个 Campaign 运行；
- 文档 `enriching` 时禁止手工删除单元；
- `mutateStore` 串行化所有写操作；
- Campaign 运行中断后重启标记 failed，需重新创建。

## 18. AgentRun 与审计

每次子 Agent 执行写入一条 `AgentRun`：

```text
id / agent / version / stage
status: running | completed | failed | skipped
startedAt / finishedAt
model / inputHash / outputSummary
warnings / error
metrics.llmCalls / metrics.durationMs
```

- 评价：写入 `Campaign.agentRuns`，`pipeline="agent"`；
- 文档整理：写入 `StoredDocument.agentRuns`，保留最近 20 条；
- `statusOnly=1` 只返回最近 5 条；
- 子 Agent 不直接写 store，持久化由 MainAgent/文档服务完成。
