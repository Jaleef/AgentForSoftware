# 检索：从词面匹配到义务级混合召回

本文说明当前一致性评价系统的检索层设计、实现和配置。目标是让“需求单元 → 候选设计单元”的召回更完整，同时保持可解释、可回退和可测试。

---

## 1. 设计目标

需求→设计不是一对一匹配：

- 一条需求可能由多个设计单元共同实现；
- 一个设计单元可能只覆盖需求的一部分义务；
- 一个设计单元可能服务多条需求；
- 正确设计不一定和需求使用相同词汇。

因此检索层不能只回答“这条需求像不像这个设计”，而应该回答：

> 这条需求的每一条原子义务，可能被哪些设计义务/设计单元覆盖？

当前实现采用：

```text
需求义务
  ├─ BM25F 稀疏召回
  ├─ Dense 语义召回（可选）
  ├─ Legacy 词面召回
  └─ RRF 融合 + 结构重排
        → 设计单元候选 Top 8
        → 评价引擎取 Top 6 交给 LLM
```

## 2. 检索单位：从需求单元下沉到义务

### 2.1 需求侧

每条需求由 `requirementObligations()` 转成稳定编号：

```text
O1：输入管理员用户名和密码
O2：后端匹配用户名密码
O3：认证失败提示错误
```

义务编号会同时用于：

- 检索查询；
- LLM 覆盖矩阵；
- 关系详情 UI；
- 覆盖率与置信度计算。

### 2.2 设计侧

设计单元会建立两类文本：

1. **设计单元整体文本**：名称、摘要、描述、接口、输入输出、义务、关键词、字段；
2. **设计义务文本**：每个设计义务单独一条，并带上设计单元名称。

这样检索到某条设计义务时，可以回溯到它所属的设计单元。

---

## 3. 三路召回

### 3.1 BM25F：字段加权词面召回

BM25F 适合接口名、字段名、模块名、专有名词和英文标识符。

字段及权重：

| 字段                     | 权重 |
| ------------------------ | ---: |
| 名称 `name`            |  3.0 |
| 接口 `interface`       |  2.5 |
| 设计义务 `obligations` |  2.0 |
| 字段 `fields`          |  1.5 |
| 摘要 `summary`         |  1.5 |
| 关键词 `keywords`      |  1.2 |
| 描述 `description`     |  1.0 |
| 输入输出 `inputOutput` |  1.0 |
| 子系统 `subsystem`     |  0.8 |

实现参数：

```text
k1 = 1.35
b  = 0.72
```

每个字段单独计算 token 频率和长度，再按字段权重累加：

```text
BM25F(q, d) =
  Σ_term IDF(term)
  × Σ_field weight_field
    × tf_field(term) × (k1 + 1)
      / (tf_field(term) + k1 × (1 - b + b × len_field / avgLen_field))
```

每个义务查询取 BM25F 前 16 个设计单元。

优点：

- 对 `deleteDataBase`、`SYS-4`、`DB-2` 这类标识符非常敏感；
- 不需要训练；
- 可解释；
- 没有外部服务时仍然可用。

### 3.2 Dense：可选语义召回

Dense 通道解决同义改写，例如：

```text
需求：删除数据库
设计：移除持久化存储
```

向量文档包括：

- 每个设计单元一条整体文本；
- 每个设计义务一条文本（最多 8 条/单元），并带上设计单元名称。

需求侧对每条义务生成查询向量，按余弦相似度召回，同一设计单元取最大值。

向量归一化后使用点积计算余弦相似度。

#### 配置

Dense 默认关闭，只有配置以下变量才启用：

```dotenv
EMBEDDING_MODEL=bge-m3
EMBEDDING_BASE_URL=https://your-embedding-gateway/v1
EMBEDDING_API_KEY=your-embedding-key

# 可选
EMBEDDING_BATCH_SIZE=32
EMBEDDING_TIMEOUT_MS=60000
```

要求后端提供 OpenAI 兼容接口：

```http
POST {EMBEDDING_BASE_URL}/embeddings
Authorization: Bearer {EMBEDDING_API_KEY}

{
  "model": "bge-m3",
  "input": ["文本1", "文本2"]
}
```

响应：

```json
{
  "data": [
    { "index": 0, "embedding": [0.1, 0.2] },
    { "index": 1, "embedding": [0.3, 0.4] }
  ]
}
```

#### 缓存

Embedding 结果在进程内按：

```text
baseUrl + model + sha256(text)
```

缓存，避免同一设计文档重复编码。

#### 失败回退

如果 embedding 未配置、网络失败、返回格式异常：

- 不阻断评价；
- 自动退回 BM25F + Legacy；
- 在评价 warnings 中记录原因。

### 3.3 Legacy：保留原有词面通道

原有 `rankDesignCandidates()` 继续保留，作为兜底和补充：

```text
overlapScore × 0.68
+ Jaccard × 0.22
+ 类型亲和度
+ 同子系统加分
+ 标题/名称重合度 × 0.14
```

它不按义务查询，而是按整条需求查询一次，作为独立通道参与融合。

---

## 4. RRF 融合

三路结果分数不在同一尺度，直接加权不稳定。当前使用 Reciprocal Rank Fusion：

```text
RRF(d) = Σ_channel 1 / (k + rank_channel(d))
```

其中：

```text
k = 60
BM25F 每义务取 Top 16
Dense 每义务取 Top 16
Legacy 每需求取 Top 16
```

同一个设计单元在不同义务中被召回时，RRF 分数累加。

### 结构重排

融合后再乘结构系数：

```text
score =
  RRF
  × (1 + 类型亲和度 + 同子系统加分 + 标题/名称重合度 × 0.14)
  × (1 + min(0.2, 命中的义务数 × 0.04))
```

含义：

- 类型越匹配，分数越高；
- 同子系统加分；
- 标题/名称越接近，分数越高；
- 被越多条需求义务召回，分数越高。

最终每条需求返回 Top 8，评价引擎再取 Top 6 发给 LLM。

## 5. 评价引擎接入

入口在 [`runEvaluation`](../server/src/evaluation/engine.ts)。

需求→设计阶段：

```text
构建 HybridRetriever
  ├─ 构建 BM25F 索引
  ├─ 构建 Legacy 索引
  └─ 尝试构建 Dense 索引（可选）
        ↓
逐条需求 rank()
        ↓
top 8 候选
        ↓
取 top 6 构造 LLM payload
```

如果混合检索初始化失败：

```text
fallback → rankDesignCandidates（原词面检索）
```

如果某条需求混合检索没有结果：

```text
fallback → rankDesignCandidates
```

因此新增检索层不会让评价完全失败。

---

## 6. 为什么不做纯向量检索

不采用“只用 embedding”的原因：

1. 接口名、字段名、错误码、模块编号需要精确匹配；
2. 中文软件文档中的术语和缩写不稳定；
3. 向量模型可能把“删除数据库”和“数据库管理”判得很近；
4. 向量分数不可解释；
5. 纯向量检索对长设计单元容易稀释。

混合检索的分工是：

```text
BM25F：保住精确词和标识符
Dense：补充语义改写
Legacy：保留原系统行为作为兜底
RRF：稳定融合
结构重排：利用子系统/类型/义务命中
```

## 7. Cross-Encoder 重排（可选）

默认使用“RRF + 结构特征重排”。如果配置了独立 reranker 服务，会在 RRF Top 20 后增加一层 Cross-Encoder：

```text
Top 20 → Cross-Encoder → Top 8 → 评价引擎取 Top 6
```

配置：

```dotenv
RERANK_MODEL=bge-reranker-v2-m3
RERANK_BASE_URL=http://127.0.0.1:8001/v1
RERANK_API_KEY=
RERANK_TIMEOUT_MS=60000
```

请求格式：

```http
POST {RERANK_BASE_URL}/rerank
Authorization: Bearer {RERANK_API_KEY}

{
  "model": "bge-reranker-v2-m3",
  "query": "需求标题 + 义务文本",
  "documents": ["设计单元名称 + 摘要 + 义务"],
  "top_n": 8
}
```

响应：

```json
{
  "results": [
    { "index": 0, "relevance_score": 0.91 },
    { "index": 3, "relevance_score": 0.72 }
  ]
}
```

行为：

- 未配置 `RERANK_MODEL` 时完全跳过；
- 每个需求一次调用，适合高精度、低吞吐场景；
- 调用失败只记录 warning，回退到 RRF 结果；
- 不阻断评价。

### 异构图召回

共享术语、接口、字段、章节等图路径还没有作为独立通道接入。当前已经把这些信息放在 BM25F 字段、Dense 文本和结构加分中，后续可以升级为图召回。

## 8. 验证

运行：

```bash
pnpm retrieval:smoke
```

会解析示例需求/设计文档，打印：

- 需求数；
- 设计单元数；
- Dense 是否启用；
- 每条需求 Top 8 候选；
- 每个候选命中的通道；
- 命中的义务数。

示例输出（未配置 embedding）：

```text
{
  requirements: 86,
  designUnits: 63,
  denseEnabled: false,
  warnings: []
}

== SRS-OTH-001 ...
SDD-MOD-013 部件级别故障检测 score=0.0777 hits=3
  channels={"bm25":1,"dense":null,"legacy":8}
```

### 质量指标

建议建立人工标注集后测：

```text
Recall@6
Recall@10
MRR
nDCG
每义务候选召回率
最终覆盖状态准确率
```

对比：

```text
A. 原词面检索
B. 义务级 BM25F + Legacy
C. B + Dense + RRF
```

## 9. 配置与环境说明

开发环境读取根目录 `.env`：

```dotenv
# 可选：启用语义召回
EMBEDDING_MODEL=bge-m3
EMBEDDING_BASE_URL=http://127.0.0.1:8000/v1
EMBEDDING_API_KEY=local-key
```

生产环境：

- 不读取 `.env`；
- 通过部署环境变量设置 `EMBEDDING_*`；
- 未配置时自动只使用 BM25F + Legacy。

注意：

- Embedding API Key 不会返回前端；
- 设计文档文本会发送到配置的 embedding 服务；
- 如果文档不能出内网，请使用本地 embedding 服务。

## 11. 后续优化

1. 增加金标准数据，量化 Recall@6；
2. 为现有 Cross-Encoder 增加批处理、缓存和限流；
3. 按义务而不是按需求做最终 LLM 判定，进一步降低输入；
4. 加 BM25 倒排索引持久化，避免每次评价重建；
5. 把设计指纹作为缓存键，文档不变时复用向量和候选；
6. 增加图召回通道（共享术语/接口/字段/章节）；
7. 对候选分数做校准，并支持 Top K 自适应。
