# 文档管理规范

本规范定义本项目文档的创建、评审、发布、废弃和归档方式。目标是避免文档漂移，保证 README 始终是可运行的入口，docs 始终反映当前系统。

## 1. 基本原则

1. **Docs-as-Code**：文档与代码同仓库、同分支、同 PR、同评审。
2. **单一来源**：同一事实只在一个文档维护，其他位置只放链接。
3. **README 稳定**：README 只放运行契约；功能、API、状态、配置细节放 docs。
4. **可追溯**：正式文档有 ID、owner、status、last_reviewed 和 related_code。
5. **可废弃**：旧文档不删除，标记 `deprecated` 后归档。
6. **可评审**：正式文档至少经过一名非作者 review。
7. **不写敏感信息**：API Key、Token、个人路径和真实生产数据不进入文档。

## 2. 文档类型

| 类型 | 示例 | 主要内容 | 更新时机 |
| --- | --- | --- | --- |
| 入口文档 | `README.md` | 安装、启动、运行契约、文档入口 | 运行契约变化 |
| 产品文档 | `产品需求与范围.md` | 目标、用户、场景、非目标、验收 | 产品范围变化 |
| 用户文档 | `功能与界面.md` | 页面能力、操作、截图 | UI/交互变化 |
| 设计文档 | `数据流.md`、`ARCHITECTURE.md` | 调用链、模块、存储 | 代码结构/流程变化 |
| 算法/口径 | `EVALUATION.md`、`检索.md` | 状态、覆盖率、置信度、检索 | 算法/提示词变化 |
| 接口文档 | `API.md` | 路由、请求、响应 | API 变化 |
| 运维文档 | `配置与运行.md` | 配置、部署、排障 | 配置/部署变化 |
| 质量文档 | `测试与验收.md` | 测试策略、验收 | 测试/门禁变化 |
| 项目文档 | `限制与路线图.md`、`CHANGELOG.md` | 限制、计划、版本 | 发布/规划变化 |
| 决策记录 | `adr/ADR-*.md` | 背景、决策、替代方案、后果 | 关键决策发生时 |
| 归档 | `99-归档/`（按需创建） | 已废弃文档 | 文档废弃时 |

## 3. 元数据

正式文档必须包含：

```yaml
---
id: DOC-XXX-001
title: 文档标题
status: approved
owner: role-or-person
reviewers:
  - reviewer-role
last_reviewed: 2026-11-08
related_code:
  - server/src/evaluation
supersedes: ""
---
```

- `id`：稳定标识，不随文件名修改；
- `status`：`draft` / `in-review` / `approved` / `deprecated`；
- `owner`：内容准确性负责人；
- `reviewers`：最近一次评审人；
- `last_reviewed`：最近一次实质评审日期；
- `related_code`：代码目录或文件，用于追溯；
- `supersedes`：被本文档替代的旧文档/ADR ID。

`README.md`、`CHANGELOG.md` 不需要 frontmatter。

## 4. 生命周期

```text
Draft → In Review → Approved → Deprecated → Archived
```

| 状态 | 含义 | 允许被引用 |
| --- | --- | --- |
| draft | 作者编写中，内容可能不完整 | 否 |
| in-review | 已提交评审，等待 reviewer | 仅评审上下文 |
| approved | 当前有效版本 | 是 |
| deprecated | 已被替代，保留历史 | 仅历史追溯 |
| archived | 已移入归档目录（如需要） | 否 |

文档废弃时：

1. 状态改为 `deprecated`；
2. 写明替代文档或废弃原因；
3. 从 `docs/README.md` 当前索引移除或标注；
4. 更新引用它的文档链接；
5. 确需保留历史时，再创建 `docs/99-归档/` 并移入。

## 5. 角色

| 角色 | 职责 |
| --- | --- |
| Owner | 保证文档与当前实现一致，响应评审意见 |
| Reviewer | 检查准确性、完整性、链接、过期内容和安全信息 |
| Approver | 确认文档可以发布；小团队可由 tech-lead 兼任 |
| Tech Lead | 维护文档体系、索引、模板和季度审计 |
| QA | 维护测试策略、验收标准和验证记录 |
| Ops | 维护部署、配置、备份和排障文档 |

小团队允许一人多角色，但架构、评价口径、检索、安全相关文档必须有第二人 review。

## 6. 评审流程

### 6.1 功能 PR

1. 修改代码；
2. 同步更新受影响的功能/数据流/API/配置文档；
3. 在 PR 描述中列出文档变更；
4. Reviewer 使用 [评审清单](templates/评审清单.md) 检查；
5. 合并后更新 `CHANGELOG.md`。

### 6.2 架构/算法变更

1. 新增或更新 ADR；
2. 更新 `ARCHITECTURE.md`、`EVALUATION.md` 或 `检索.md`；
3. 更新 `数据流.md` 中受影响操作；
4. 架构 owner review；
5. 合并后更新索引。

### 6.3 发布

1. 检查所有 `approved` 文档的 `last_reviewed`；
2. 检查示例数字、截图和接口是否过期；
3. 更新 `CHANGELOG.md`；
4. 打版本标签；
5. 归档已废弃文档。

### 6.4 季度审计

每季度检查：

- 文档链接是否有效；
- 示例数字是否仍可复现；
- `related_code` 是否还存在；
- 是否有 `approved` 文档描述已删除功能；
- 是否需要新增 ADR 或归档。

## 7. 写作规范

- 使用 Markdown，文件名使用中文或稳定英文名；
- 图优先使用 Mermaid 或 ASCII，避免只放不可编辑的截图；
- 代码路径使用相对链接，例如 `../server/src/evaluation/engine.ts`；
- 不复制其他文档的表格，使用链接；
- 示例命令必须可在当前仓库执行；
- 示例密钥一律使用占位符；
- 变更历史写入 `CHANGELOG.md`，不在正文堆叠“更新日志”；
- 术语保持稳定，首次出现时写全称。

## 8. README 不变量

README 只允许包含：

- 系统定位；
- 运行要求；
- 安装和启动命令；
- 开发/生产地址；
- 数据目录、配置来源、API 前缀、本地单用户等运行契约；
- 文档入口；
- 安全边界。

README 不允许包含：

- 示例统计数字；
- 功能矩阵；
- API 路由表；
- 环境变量完整表；
- 状态/评分定义；
- 架构细节；
- 截图；
- 已知限制列表；
- 演示数据说明。

## 10. 违规处理

出现以下情况时，文档不视为 `approved`：

- 无 owner 或 last_reviewed；
- 描述与当前代码不一致；
- 仍引用已删除接口/文件；
- 在 README 中维护易变内容；
- 复制了其他文档的单一来源表格；
- 包含真实 API Key 或敏感数据。

Tech lead 在季度审计中将其标记为 `in-review` 或 `deprecated`，并指定 owner 修正。
