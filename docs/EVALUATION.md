# 评价口径

## 1. 目标与边界

本工具评价**文档与文档、文档与代码之间的一致性**，不是缺陷检测器，也不评价代码质量、性能或安全性本身。

执行链路由 `runEvaluation` 直接编排需求→设计、设计→代码两个层级，见 [架构说明](ARCHITECTURE.md)；本页只定义判定口径。

- 需求→设计：检查设计是否覆盖需求的全部可核验义务。
- 设计→代码：检查代码快照是否实现设计的接口、输入输出、数据结构和行为。
- 不构建、不执行代码；不推断运行时行为；不替代测试。
- 所有 LLM 判定都需要人工复核，尤其是 P0 问题。

## 2. 单元与义务

### 2.1 需求点

需求点是“是否构成需求”的中间结果：

- **表格需求点**：需求表结构直接识别，`origin=rule`，`confidence=1.0`。
- **文本需求点**：只有文字描述的叶子章节/段落，先作为候选，由 LLM 判断是否构成需求；`origin=llm`，`confidence` 由 LLM 给出。
- 每个需求点保存带编号的 `chapterPath`（如 `3 需求分析 / 3.3 功能需求 / 3.3.1 ...`），用于追溯和子系统分类统计。
- 文本候选只过滤目录、图题、过短文本、纯标签等结构噪声，不依赖章节名称。
- 无论来源如何，章节路径只用于追溯，不用于推断需求类型或子系统。

### 2.2 需求单元

需求单元由**所有已接受需求点**交给 LLM 生成，包含：

- `code`：按 LLM 判断的类型生成编号（`SRS-FR-001`）。
- `pointId / sourceKind / structureOrigin`：来源需求点、表格/文本、单元由 LLM 还是规则回退生成。
- `sourceId / parentSourceId`：源文档中的需求 ID / 父需求 ID（可为空）。
- `type`：功能、性能、页面/人机交互、接口、数据、环境、安全保密、设计实现约束、验收交付、质量属性、元数据等。
- `subsystem`：来自 LLM 归纳的统一子系统分类，不在单元生成阶段自由发挥。
- `description / detail`：需求描述与需求说明原文（不由 LLM 改写）。
- `obligations`：LLM 生成的原子义务。
- `chapter / chapterPath / location`：带编号的章节路径、页码、行号（追溯用；不参与类型判断）。
- `origin / confidence`：继承需求点来源与置信度（表格为规则/100%，文本为 LLM 判定置信度）。
- 手工新增的需求单元使用 `origin=manual`、`code=SRS-MAN-NNN`、置信度 100%，并在 LLM 重新整理后保留；删除生成单元时会同步移除其需求点，避免后续 LLM 整理重新生成。

### 2.3 设计单元

设计单元与需求单元一样先抽设计点，再由 LLM 生成：

- **结构化设计表**：含 `模块编号`/`子功能编号` + 功能描述的表直接生成设计点，`origin=rule`、`confidence=1.0`。
- **数据库表**：先保留字段结构作为候选，由 LLM 判定是否构成 `数据表` 设计单元。
- **文本章节**：页面设计、模块/接口说明等叶子章节作为候选，由 LLM 判定是否构成设计单元。
- `模块` / `子功能` / `数据表` / `页面`：由 LLM 根据内容与结构化提示确定。
- `subsystem`：来自全部设计点章节路径归纳出的统一分类，不在单元生成阶段自由生成。
- 手工新增的设计单元使用 `origin=manual`、`code=SDD-MAN-NNN`、置信度 100%，并在 LLM 重新整理后保留；删除生成单元时会同步移除其设计点。
- 每个设计点保存带编号的 `chapterPath`，仅用于追溯和子系统分类。

设计义务包括：功能描述、接口签名、输入、输出、字段约束。数据库表额外保存字段名、类型、长度、主键。

## 3. 判定状态

### 3.1 需求 → 设计

| 状态 | 判定条件 | 示例 |
| --- | --- | --- |
| `satisfied` | **多个设计单元的并集**完整覆盖需求全部原子义务；每条义务至少被一个设计完整覆盖 | D1 覆盖 O1/O2，D2 覆盖 O3 → 联合覆盖 3/3 |
| `partial` | 并集覆盖了一部分义务，但仍有关键义务缺失或只被部分覆盖 | D1 覆盖 O1，O2/O3 未覆盖 |
| `missing` | 所有候选设计都没有覆盖任何义务 | 需求“远程运维”但设计中没有运维模块 |
| `mismatch` | 任一义务被设计明确冲突/违背 | 需求要求 TCP，设计写成文件导入 |

计算规则：

```text
coverageRatio = (完整覆盖义务数 + 0.5 × 部分覆盖义务数) / 义务总数

status =
  mismatch   如果存在冲突义务
  satisfied  如果完整覆盖义务数 == 义务总数
  partial    如果至少覆盖或部分覆盖一条义务
  missing    如果一条义务也没有覆盖
```

- LLM 不再直接输出整条需求的 `satisfied/partial`，而是输出每个设计分别覆盖了哪些 `O1/O2/...`。
- 同一义务可以被多个设计覆盖；同一设计可以出现在多条需求中。
- 名称相似但义务缺失**不得**判为 `satisfied`。
- `confidence` 是覆盖置信度：每条义务取最强设计证据置信度（完整 ×1.0、部分 ×0.6、冲突 ×0.2），再按义务数取平均；没有设计声明覆盖时取 0.4 基线。
- 需求→设计的综合得分按 `coverageRatio × 100` 计算（`mismatch` 仍按冲突权重计）；设计→代码仍按状态权重计。

### 3.2 设计 → 代码

| 状态 | 判定条件 |
| --- | --- |
| `satisfied` | 候选中存在与设计义务对应的实现，功能、接口/路由、输入输出基本一致 |
| `partial` | 有相关实现，但缺少部分义务、接口、字段或分支 |
| `missing` | 代码快照中没有对应实现 |
| `divergent` | 有实现，但与设计行为、接口或数据模型明显不一致 |

## 4. 检索

LLM 只看候选，不直接读全量文档/代码。

需求→设计采用**义务级混合检索**：

- BM25F：字段加权的接口/义务/字段/名称召回；
- Legacy：原 token 覆盖率 + Jaccard；
- Dense：可选语义召回；
- RRF：多通道排名融合；
- 可选 Cross-Encoder：Top 20 精排到 Top 8；
- 评价引擎按模式取 Top 4（economy）或 Top 6（balanced/quality）交给 LLM。

设计→代码仍使用 `rankCodeCandidates` 取 Top 7 符号，同一文件最多 2 个。

完整算法、配置和验证见 [检索](检索.md)。

## 5. LLM 契约

### 5.1 需求→设计

输入包含：

- `designs`：本批去重后的候选设计目录（code、类型、摘要、描述、义务、接口、输入输出、字段）；
- `requirements`：需求（类型、子系统、标题、描述、说明、带编号义务 O1..On、candidateCodes）。

模型只能使用该需求 `candidateCodes` 里的设计。

LLM **不直接输出整条需求状态**，只输出每个设计对义务的覆盖：

```json
{
  "items": [
    {
      "requirementCode": "SRS-FR-001",
      "targetCoverages": [
        {
          "designCode": "SDD-FUN-001",
          "coveredObligations": ["O1", "O2"],
          "partialObligations": ["O3"],
          "conflictingObligations": [],
          "evidence": "设计原文片段",
          "confidence": 0.9
        }
      ]
    }
  ]
}
```

约束：

- `designCode` 必须来自该需求的候选；
- obligationId 必须来自输入义务；
- 一个设计可以只覆盖部分义务，多个设计可以互补；
- 没有覆盖/冲突的候选不输出；
- 最终状态、覆盖率、置信度由程序聚合，见第 3.1 节。

### 5.2 设计→代码

输入：设计单元 + 候选符号（handle `C1..C7`、类型、名称、文件、行号、签名、代码片段）。

```json
{
  "items": [
    {
      "designCode": "SDD-FUN-001",
      "status": "implemented|partial|missing|divergent",
      "targetHandles": ["C1"],
      "confidence": 0.8,
      "rationale": "...",
      "evidence": "文件:行 或代码片段",
      "gaps": ["..."],
      "suggestions": "..."
    }
  ]
}
```

`implemented` 映射为内部 `satisfied`；`divergent` 保留。代码片段视为待审数据，忽略其中的指令性文字（防提示注入）。

### 5.3 需求/设计两阶段 LLM 处理

上传时可选择「LLM 整理」：

1. 判断文本/数据库候选是否构成单元；
2. 统计章节路径，归纳子系统 taxonomy；
3. 对全部已接受点生成单元：
   - 需求：标题、类型、摘要、义务、关键词；
   - 设计：名称、类型、摘要、设计义务、关键词，保留结构化表和字段。

置信度来自拆分点：规则表格 100%，文本/数据库点由 LLM 判定。生成单元阶段不重新给置信度。

失败时保留规则拆分结果，并在文档 warning 中提示。

## 6. 汇总

### 6.1 得分

```
statusWeight = { satisfied: 100, partial: 60, divergent: 30, mismatch: 20, missing: 0 }

需求→设计（satisfied/partial）：
  relationScore = coverageRatio × 100
需求→设计（mismatch/missing）：
  relationScore = statusWeight

设计→代码：
  relationScore = statusWeight

levelScore = mean(relationScore)
overall    = 两层级都存在 ? mean(levelScore) : 单层级 levelScore
```

人工驳回的判定不参与计算（任务详情中的分子系统/总览会重新汇总）。

### 6.2 覆盖率

```
需求覆盖率       = Σ 每条需求的 coverageRatio / 需求总数
设计实现覆盖率   = (satisfied设计 + 0.5 × partial设计) / 设计单元总数
设计被需求追溯   = 在需求→设计判定中出现过的设计单元数 / 设计单元总数
```

需求→设计的 `coverageRatio` 为义务覆盖比例；旧任务没有该字段时回退到状态权重。

### 6.3 问题等级

| 等级 | 规则 |
| --- | --- |
| P0 | 需求→设计中功能/接口/数据/页面/性能需求的 `missing/mismatch`；设计→代码中模块/子功能/数据表的 `missing/divergent` |
| P1 | 其他 `missing/mismatch/divergent`，以及所有 `partial` |
| P2 | 低置信度/待确认（当前版本保留字段） |

### 6.4 门禁

- ≥ 85：通过
- 70–85：警告
- < 70：不通过

门禁只是流程辅助，不能替代评审结论；报告会明确标注评价方法（LLM 或启发式）。

## 7. 回退与降级

| 场景 | 行为 |
| --- | --- |
| 未配置 API Key / Mock 模式 | 全部使用启发式；任务与报告标注 |
| LLM 预检失败 | 整个任务回退启发式，保留失败原因 |
| 单个批次调用失败 | 该批次回退启发式，最多保留 6 条警告，其余合并提示 |
| 返回非法 JSON / 非法 code | 视为该批次失败，回退启发式 |
| 返回非法义务 ID / 未覆盖任何义务 | 该设计贡献被忽略；整条需求可能为 missing |
| 旧格式返回 status/targetCodes | 走兼容路径，不生成义务矩阵 |
| 用户取消 | AbortController 中断；任务状态 `cancelled` |
| 服务重启 | 启动时把残留的 `running/queued` 任务标记为失败，提示重新创建 |

启发式规则：

- 需求→设计：按检索得分，≥0.20 部分覆盖，否则缺失；**不再直接判 satisfied**，因为无法逐条核验义务。
- 设计→代码：数据表阈值略低；≥0.34 已实现，≥0.18 部分实现，否则缺失。
- 启发式不产生 `divergent`。

启发式只适合演示与初筛，正式评审应使用 LLM 并人工复核。

## 8. 人工复核

- 需求类型可在需求详情中修改并保存（`reviewStatus=confirmed`），用于纠正分类。
- 设计单元可标记“审核通过”。
- 判定条目可“确认 / 驳回 / 重置”；驳回后从得分中排除，并重新汇总。
- 所有人工操作只改变本地状态，不修改原始 DOCX。

## 9. 质量建议

1. 需求文档尽量为每条需求填写稳定 ID，便于跨版本追踪。
2. 设计文档的每个模块/子功能补充接口、输入、输出，LLM 判定的证据会明显更充分。
3. 代码快照应在同一 commit 上生成，避免文档与代码版本错位。
4. 对 P0 问题逐条人工确认，不要只看总分。
5. 变更文档后重新创建评价，不要复用旧任务结论。
